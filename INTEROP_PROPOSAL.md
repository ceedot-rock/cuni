# CuNi Cross-Program Interop — Draft Proposal

**Status: RATIFIED and IMPLEMENTED.** All six numbered decisions below are folded into SPEC.md §16 (`link`) and implemented in all three toy backends (`src/codegen_{py,go,js}.rs`), gated by a real compile-or-refuse check (`src/checks.rs::find_bad_link_type`) restricting v1 to scalar param/return types. Verified with a genuine cross-language proof, not just same-language self-consistency: `tests/conformance.rs::link_interop_go_server_python_client` compiles `examples/link.cuni` to Go and Python, starts the Go binary as a real server process, and asserts a Python-compiled client gets the correct answer back over an actual socket — plus manual verification of all three pairwise combinations (Go server/Python client, Python server/JS client, JS server/Go client) during development. The only item not carried into SPEC.md verbatim is the exact grammar, which lives in `GRAMMAR.md` instead (`link_decl`), matching how `fail`/`enum` were handled.

**The problem.** CuNi's exactness contract (§2) governs a single *compilation*: one CuNi source file, compiled to one target, behaves identically to the same source compiled to any other target. It says nothing about two *separately compiled* CuNi programs — say, one running as a Go service, another as a Python script — that need to talk to each other at runtime in a real deployed system. `ext` (§9) doesn't help here: it lets one compilation call into that same target's native code, not into another CuNi program running as a different target. This is undesigned territory.

**Method.** Four independent positions were gathered — one advocate each for Python, Go, and JS (arguing for their own ecosystem's idioms), and one for "CuNi Core" (arguing to protect the exactness contract and the small-core tenets against ecosystem-specific pressure). Summarized below, then synthesized into a single recommendation.

---

## The four positions

**Python** — plain HTTP + JSON, request/response. Zero codegen, zero new toolchain; `httpx`/async Python is the ecosystem's default reflex. Flagged a real risk: JSON has no canonical integer type, and Python's arbitrary-precision ints can silently lose precision if a receiving target's number type is narrower. Asked whether exactness extends across a process boundary at all.

**Go** — gRPC over protobuf. Idiomatic for Go production services, deploys as the same static binary Go already ships, gives Go's static type system a compile-time-checkable schema. Conceded, unprompted, that Python's and JS's gRPC bindings are heavier and more native-dependency-laden than their idiomatic style — and asked whether a schema-typed IDL forces Python/JS to accept static contracts they don't natively have, making the "interop layer" quietly Go's design imposed on the other two.

**JS** — HTTP + JSON (+ WebSockets for streaming), using only what Node ships natively (`http`, `fetch`, `JSON.parse`/`stringify`). Explicitly rejected gRPC: native bindings reintroduce exactly the npm-ecosystem fragility (`node-gyp`, ABI drift across Node versions) that "compile-or-refuse" should want to avoid. Independently hit the same numeric-precision concern Python raised, from the other direction: `JSON.stringify` silently loses precision above 2^53, and Go's int64/Python's bigints can produce values JS can't round-trip.

**CuNi Core** — refused to let "byte-identical behavior" extend across a process boundary; that's a compilation-time guarantee, not a runtime one. Proposed a new core keyword, `link`, describing a typed message contract *in CuNi syntax*, from which each target's compiler deterministically generates its own transport code — the guarantee is "same observable contract" (message shape, validation behavior, error taxonomy), not "same bytes on the wire." Vetoed two things pre-emptively, even under unanimous agreement from the other three: **configurable transport** (reintroduces per-target tiers through the back door — exactly what single-tier support, §2, exists to prevent) and **a schema format borrowed from a target-native artifact** (a `.proto` file or JSON Schema doc CuNi merely wraps — "`ext` wearing a costume," not a core feature).

---

## Synthesis

Two independent signals point the same direction. First, two of three language advocates (Python, JS) converged on HTTP+JSON without being asked to agree, and Go's own advocate voluntarily flagged the same worry CuNi Core would raise (imposing one target's schema culture on the others). Second, JS's specific objection to gRPC — native bindings undermining "compile-or-refuse" — is really CuNi Core's own concern voiced from a different seat. Nobody defended configurable transport; it just wasn't proposed as a real option once each advocate is read closely.

**Recommendation:** adopt CuNi Core's `link` proposal as the shape of the feature, with the wire format resolved as an *implementation decision the compiler makes once for all targets* — not a per-program configuration choice, and not exposed in CuNi source at all:

1. **New keyword `link`** — declares a typed message contract in CuNi syntax (field names + CuNi's existing types: `int`, `str`, `list<T>`, `typ`-defined structs, etc.), the same way `typ` declares a struct. Each target's compiler emits that target's own client/server stub deterministically from the same `link` declaration — no target-specific config leaks into CuNi source, matching `typ`/`iface`'s existing pattern of one CuNi declaration, N target-native realizations.
2. **Wire substrate: plain HTTP + JSON**, not gRPC/protobuf — chosen because it's the only option that avoids adding a native-dependency toolchain requirement (`node-gyp`, C-extension builds) to any of the three v1 targets, which is a correctness-adjacent concern (compile-or-refuse shouldn't depend on a package manager successfully building a C extension), not just a convenience one. This is a concession from Go's advocate's preference, not a compromise — Go's own JSON support (`encoding/json`) is first-class, so nothing is lost there; what's lost is protobuf's compile-time schema checking on the Go side specifically, a real, named tradeoff.
3. **Numeric exactness across the wire, resolved explicitly, not left implicit:** both Python and JS independently flagged the same gap from opposite directions (arbitrary-precision/int64 vs. float64's 2^53 ceiling). A `link` contract's compiler must apply compile-or-refuse here too: any `int` field is wire-encoded as a decimal string (not a JSON number), and the compiler rejects a `link` declaration if a target can't prove it round-trips that string back to the same integer losslessly. This is the same "reject rather than approximate" posture §2 already requires elsewhere — it just hasn't had a wire boundary to apply to before now.
4. **Error taxonomy is part of the contract, not an implementation detail** — per CuNi Core's requirement, a malformed message must fail the same observable way (same error shape reported back to the caller) on all three targets, checked the same way the stdlib table (§15) already requires all three target mappings to be specified before a name is added.

**What this deliberately does not do:** it does not attempt real distributed-systems concerns (retries, timeouts, service discovery, backpressure) — those are either `ext`'s job (drop into target-native tooling for the specific non-portable operational concern) or a future, separate open item. `link` only claims to solve message-contract exactness across a process boundary, which is already a meaningfully scoped, non-trivial claim on its own.

5. **RATIFIED: `link` is synchronous request/response only in v1; streaming is deferred**, not designed here. This was the only interaction shape all three language advocates actually asked for — the JS advocate's WebSocket mention was a passing aside, not a real ask from any of the four — and it's a far smaller, more provable surface to get "same observable contract" right on before taking on a stateful-connection abstraction (which is a materially harder exactness problem: a connection has ongoing state to keep identical across targets, not just one request/response pair). Same deferral posture already used twice in this project (Rust from v1 targets, §3; tagged unions from `enum`, §14).

6. **RATIFIED: `link` is codegen-only — it does not ship a bundled runtime.** Each target's compiler emits plain client/server stub code (an HTTP handler function, a typed client function) that the user wires into their own `main`/entry point themselves, same as every other CuNi construct emits code rather than owning a process. This matches how the toy backends already work today — `func main()`/`def main()` is emitted code the compiler writes, not a daemon CuNi runs on the user's behalf — and it keeps `link` from taking on operational concerns (port binding, TLS, graceful shutdown, restart policy) that §2's "small core over broad coverage" tenet would otherwise pull `link` toward owning. Cost: slightly more boilerplate per program (the user writes a few lines to actually start the listener) in exchange for CuNi never becoming an application-server framework by accident.

**Resolved since the draft above:**
- Exact CuNi-level syntax for `link` — settled as `link Name(params) -> type [?] do ... end`, identical to `def` minus generics, restricted to scalar param/return types (see SPEC.md §16, `GRAMMAR.md`'s `link_decl`).

All of this is now in SPEC.md (§16) and `GRAMMAR.md`; this document is kept as the design-rationale record, same as `OPEN_ITEMS_PROPOSAL.md`.
